# Shared interfaces (interface agreement for all agents)

This is the interface agreement between tasks. It **does not redefine** shapes
that already exist in code. For those it links the source of truth and names
the task that owns changes.

Status markers:

- **FIXED**: agreed (authoritative docs or existing code). Change only through an
  Interface Change Request (ICR, [AGENT_HANDOFF_PROTOCOL.md](AGENT_HANDOFF_PROTOCOL.md) §4).
- **PROPOSED**: suggested by this plan to let tasks run in parallel. The owning
  task confirms or amends it via ICR **before** dependants rely on it.
- **UNRESOLVED**: needs a decision (`D-xx`,
  [DECISIONS_AND_OPEN_QUESTIONS.md](DECISIONS_AND_OPEN_QUESTIONS.md)) or live
  evidence (`E1`–`E5`, `E17`).

## 3. Authorization (gateway)

| Item | Status | Definition |
|---|---|---|
| `ArmorIQDecision` | **FIXED shape** (`models.py`) | `outcome` (`allow`/`block`/`hold`/`unverified`), `source`, `reason?`, `enforcement_action?`, `armoriq_plan_id?`, `delegation_id?`, `decided_at`. Validators: SDK plan check ⇒ BLOCK only; HOLD only from ArmorIQ sources |
| Mapping from real SDK results/exceptions | **UNRESOLVED** (E1–E4) | Defined by P1-02 from the installed SDK source, then corrected by experiment evidence |
| `DecisionSource` label set | **PROPOSED** (D-03, ADR-009 union) | `armoriq_issuance`, `armoriq_policy_decision`, `armoriq_sdk_plan_check`, `armoriq_proxy_decision`, `tool_server_rule`, `application_rule`, `unknown` |
| Gateway Python interface | **PROPOSED** (P1-02) | See below. The only `armoriq_sdk` importer |

```python
# services/authorization/armoriq_gateway.py  (PROPOSED signatures; P1-02 confirms via ICR)
class ArmorIQGateway:
    def __init__(self, settings) -> None: ...            # one SDK client per configured member, each with its own lock
    async def start_plan(self, ctx: RequestContext, plan: PlanProposal) -> PlanHandle: ...
        # one ArmorIQ plan per request; mint once; failure -> PlanHandle with ArmorIQDecision(outcome=BLOCK|UNVERIFIED)
    async def invoke_step(self, handle: PlanHandle, step_index: int) -> StepOutcome: ...
        # signs _ctx (P1-04) with a fresh jti, invokes under the same plan/token; HOLD -> waits/polls per verified SDK behavior
    async def attempt_off_plan(self, handle: PlanHandle, tool: ToolName, arguments: dict) -> ArmorIQDecision: ...
        # routes an off-plan tool request through the SDK plan-check path; NEVER executes; label per E2

@dataclass(frozen=True)
class StepOutcome:
    decision: ArmorIQDecision
    approval: ApprovalStatus | None          # present when a HOLD occurred
    invocation: ToolInvocationResult | None  # present only when the call reached the tool server
```

Fail-closed rule (**FIXED**, PRD §0.6): any exception, timeout, or
unverifiable state becomes `outcome=unverified` or `block` with a truthful
source (`unknown` if the layer cannot be determined). Never `allow`.

Tool result shape (P2-06 emits it, `services/toolserver/schemas.py`; the
gateway, P1-02, parses it in `ArmorIQGateway._map_success`). The payload is
the MCP `CallToolResult` (the JSON-RPC `result`, as `MCPInvocationResult.result`):

```jsonc
// success: exactly one ledger row (execution_status=executed) exists for this jti
{"content": [{"type": "text", "text": "<JSON of the P2-02 result model>"}],
 "isError": false,
 "_meta": {"ledger_entry_id": "<tool_execution_ledger.id as a decimal string>"}}

// rejection or failure
{"content": [{"type": "text", "text": "{\"code\": \"<§4 code>\", \"message\": \"<fixed text>\"}"}],
 "isError": true,
 "_meta": {"ledger_entry_id": "<id>"}}      // only when THIS call has its own row:
                                             // invalid_arguments / out_of_scope
                                             // (rejected_by_tool_server) or a handler
                                             // failure (code internal, execution_status=error)
// replay: "_meta": {"original_entry_id": "<id>"} when the original call's row exists
// no row (invalid_context, context_expired, unknown tool, no ledger, ...): no "_meta"
```

- `_meta` is the only place for correlation data: the text block of a success
  is the bare result model (consumers parse it with the P2-02 models), and
  `mcp==2.3.0`'s wire `CallToolResult` model ignores unknown top-level keys.
- Gateway rules: `isError` (or the SDK's `status == "error"`) is always a
  rejection; the code comes from the text block and anything outside the §4
  set becomes `internal`; EXECUTED requires `_meta.ledger_entry_id`, otherwise
  the status stays `unknown`. A rejection's `ledger_entry_id` is its own row,
  or on replay the original entry. Top-level `ledger_entry_id`/`error_code`
  keys (the earlier provisional reading) are still accepted.
- Whether `_meta` survives the ArmorIQ proxy is unverified until E1 (P1-06);
  without it a success degrades to `unknown`, never to a false EXECUTED.
- `tools/list` advertises the enforced argument model (`model_json_schema()`:
  limits, `additionalProperties: false`) plus `patternProperties: {"^_": {}}`,
  so `_ctx` and the SDK's `_policy_context` are admitted but never declared (D-05).
| Tool handler security hook | **PROPOSED** (P1-04 provides, P2-06 wires) | `verify_tool_call(endpoint, tool, raw_arguments) -> VerifiedCall(ctx, business_arguments, trace_metadata)`. Raises a rejection before any handler logic. Called for **every** product tool; there is no unguarded product tool |

Knowledge record layout written by the seed (P2-03, **PROPOSED**; read by
P2-04/P2-05/P2-08; full detail in `seed/README.md`):
`source_records` has no `version`/`review_status`/`superseded_by` columns, so
they live in `provenance` (`version` int, `review_status` ∈ `ReviewStatus`,
`superseded_by` = successor `source_id` or `null`, consistent with `status`),
next to `recorded_at`, `embed_model`, `embed_tool` (model version), `embed_dim`,
and `ingest_digest`; `created_at`/`updated_at` = the record's synthetic date.
`knowledge_chunks.tier` always equals its source's `tier`.

Search ordering and score (P2-05, `services/knowledge/retrieval.py`,
**PROPOSED**; the threshold value stays D-23/E17's): `knowledge_search_*`
runs a lexical leg (`websearch_to_tsquery`, rows with `ts_rank_cd` = 0
dropped) and a vector leg (HNSW cosine), 50 candidates each, and fuses them
with RRF (k = 60) for ORDER only: `rank` is the fused order (chunks dedupe,
then each source keeps its best chunk). `KnowledgeSearchHit.score` is the
cosine similarity `1 - (embedding <=> query_embedding)` of the returned chunk
under `EMBED_MODEL` (in [-1, 1]; seed corpus: on-topic top hits ~0.70–0.81,
off-topic or nonsense queries ~0.45–0.60). It is comparable across queries,
NOT monotonic in `rank`, and the only value `min_score` / `MIN_SCORE` filter
on (the responder's `effective_min_score` compares it); a threshold measured
on RRF sums or another model does not transfer. Both legs share one filter
clause: workspace, exact tier, `status = 'active'`, `review_status =
'authoritative'` (D-09), and the source join requires the chunk's workspace
and tier. Snippets are ≤ 400 characters: the whole chunk, else `ts_headline`
fragments around the matched terms, else the leading text. `decisions`,
`manager_guidance`, `team_notes` carry a nullable `seed_key` (0010): set on
seed rows, NULL on runtime rows. Eval case labels are never stored.

No runtime role gets `UPDATE`/`DELETE` on ledger or audit tables (append-only, PROPOSED).

2. In `guarded(...)`, call `verify_and_record(ledger, endpoint, tool, raw_arguments,
   credential_id=<bearer setting name>, ctx_secret=...)` **instead of**
   `verify_tool_call`, after the bearer check and before any handler logic.
   `credential_id` is the NAME of the setting that authenticated the call
   (`toolserver_bearer_memory` / `toolserver_bearer_workspace`;
   `SERVICE_CREDENTIAL_IDS`), never its value. It records the attempt and
   returns the same `VerifiedCall`. Fail closed: a rejection is re-raised even
   when recording it fails; an accepted call whose attempt row cannot be
   written raises `CtxRejection("internal")` and must not execute. Any other
   exception (database down during the jti claim) also means: do not execute.
3. After the handler: `ledger.append(LedgerEntry(...))` with identity fields
   from `verified.ctx` and `arguments=verified.business_arguments` (hashed,
   never stored). A post-verification rejection (`invalid_arguments`,
   `out_of_scope`, `precondition_failed`) is appended with that
   `validation_outcome` and `execution_status=rejected_by_tool_server`;
   handler failures use `validation_outcome=accepted`, `execution_status=error`
   and `error_class=type(exc).__name__`.
   `DuplicateJti` means "do not execute; reject as `replay` referencing
   `exc.existing_id`". A replay caught during verification raises
   `ReplayRejection` (a `CtxRejection`) whose `original_entry_id` is the
   original row (or None); P2-06 returns it as `_meta.original_entry_id` (§4).
4. No ledger (no `DATABASE_URL_TOOLSERVER`): rejections still answer with their
   codes, but no product tool executes (`internal` before the handler).
