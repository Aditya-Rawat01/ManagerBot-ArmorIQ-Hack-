# Shared interfaces (interface agreement for all agents)

This is the interface agreement between tasks. It **does not redefine** shapes
that already exist in code. For those it links the source of truth and names
the task that owns changes.

Status markers:

- **FIXED**: agreed (authoritative docs or existing code). Change only through an
  Interface Change Request (ICR, [AGENT_HANDOFF_PROTOCOL.md](AGENT_HANDOFF_PROTOCOL.md) §4).
- **PROPOSED**: suggested by this plan to let tasks run in parallel. The owning
  task confirms or amends it via ICR **before** dependants rely on it.
- **UNRESOLVED**: needs a decision (`D-xx`,
  [DECISIONS_AND_OPEN_QUESTIONS.md](DECISIONS_AND_OPEN_QUESTIONS.md)) or live
  evidence (`E1`–`E5`, `E17`).

## 3. Authorization (gateway)

| Item | Status | Definition |
|---|---|---|
| `ArmorIQDecision` | **FIXED shape** (`models.py`) | `outcome` (`allow`/`block`/`hold`/`unverified`), `source`, `reason?`, `enforcement_action?`, `armoriq_plan_id?`, `delegation_id?`, `decided_at`. Validators: SDK plan check ⇒ BLOCK only; HOLD only from ArmorIQ sources |
| Mapping from real SDK results/exceptions | **UNRESOLVED** (E1–E4) | Defined by P1-02 from the installed SDK source, then corrected by experiment evidence |
| `DecisionSource` label set | **PROPOSED** (D-03, ADR-009 union) | `armoriq_issuance`, `armoriq_policy_decision`, `armoriq_sdk_plan_check`, `armoriq_proxy_decision`, `tool_server_rule`, `application_rule`, `unknown` |
| Gateway Python interface | **PROPOSED** (P1-02) | See below. The only `armoriq_sdk` importer |

```python
# services/authorization/armoriq_gateway.py  (PROPOSED signatures; P1-02 confirms via ICR)
class ArmorIQGateway:
    def __init__(self, settings) -> None: ...            # one SDK client per configured member, each with its own lock
    async def start_plan(self, ctx: RequestContext, plan: PlanProposal) -> PlanHandle: ...
        # one ArmorIQ plan per request; mint once; failure -> PlanHandle with ArmorIQDecision(outcome=BLOCK|UNVERIFIED)
    async def invoke_step(self, handle: PlanHandle, step_index: int) -> StepOutcome: ...
        # signs _ctx (P1-04) with a fresh jti, invokes under the same plan/token; HOLD -> waits/polls per verified SDK behavior
    async def attempt_off_plan(self, handle: PlanHandle, tool: ToolName, arguments: dict) -> ArmorIQDecision: ...
        # routes an off-plan tool request through the SDK plan-check path; NEVER executes; label per E2

@dataclass(frozen=True)
class StepOutcome:
    decision: ArmorIQDecision
    approval: ApprovalStatus | None          # present when a HOLD occurred
    invocation: ToolInvocationResult | None  # present only when the call reached the tool server
```

Fail-closed rule (**FIXED**, PRD §0.6): any exception, timeout, or
unverifiable state becomes `outcome=unverified` or `block` with a truthful
source (`unknown` if the layer cannot be determined). Never `allow`.

P2-06 wiring notes (`services/toolserver/ledger.py`; no handler calls
`verify_tool_call` on `main` yet):

1. One pool per process: create it once with `db.create_pool(DATABASE_URL_TOOLSERVER)`
   and pass it in — `Ledger(pool=pool)`. The process owns and closes the pool.
2. In `guarded(...)`, call `verify_and_record(ledger, endpoint, tool, raw_arguments,
   credential_id=<bearer setting name>, ctx_secret=...)` **instead of**
   `verify_tool_call`, after the bearer check and before any handler logic.
   `credential_id` is the NAME of the setting that authenticated the call
   (`toolserver_bearer_memory` / `toolserver_bearer_workspace`;
   `SERVICE_CREDENTIAL_IDS`), never its value. It records the attempt and
   returns the same `VerifiedCall`. Fail closed: a rejection is re-raised even
   when recording it fails; an accepted call whose attempt row cannot be
   written raises `CtxRejection("internal")` and must not execute. Any other
   exception (database down during the jti claim) also means: do not execute.
3. After the handler: `ledger.append(LedgerEntry(...))` with identity fields
   from `verified.ctx` and `arguments=verified.business_arguments` (hashed,
   never stored). A post-verification rejection (`invalid_arguments`,
   `out_of_scope`, `precondition_failed`) is appended with that
   `validation_outcome` and `execution_status=rejected_by_tool_server`;
   handler failures use `execution_status=error` and `error_class=type(exc).__name__`.
   `DuplicateJti` means "do not execute; reject as `replay` referencing
   `exc.existing_id`".

## 13. Correlation IDs

| ID | Status | Meaning / generator |
