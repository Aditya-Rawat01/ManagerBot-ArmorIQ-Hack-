## 2. Architecture (P1-02's slice)

```text
Slack (Socket Mode) ─┐
Web demo / console ──┴─▶ apps/api: identity → planner → orchestrator
                          │      → ArmorIQGateway (services/authorization; ONLY armoriq_sdk importer)
                          │      → responder → delivery routing → audit (services/audit)
                          ▼
                      ArmorIQ (plan, intent token, policy, HOLD/console approval)
                          ▼
              services/toolserver (public HTTPS MCP: memory-mcp, workspace-mcp)
                 credential + signed _ctx → strict schemas → tier-fixed handlers
                 → services/knowledge (tool server only) → hash-chained ledger
                          ▼
              Neon PostgreSQL + pgvector (roles: backend / toolserver / migration)
```

Seven authorization layers (Arch §5.4, rules R-20..R-27): P1-02 owns layer 4
(ArmorIQ intent/plan enforcement via the gateway). It never substitutes for layers
1–3, 5–7. Backend never reads protected tables (R-20); tier is in the tool name (R-22);
tool server re-verifies everything (R-23); `_` fields are stripped and never authority (R-24).

## 8. Gateway flow + boundaries

`start_plan`: validate `PlanProposal` (contract validators already enforce step order,
endpoint match, no `_`/forbidden keys, ≤1 elevated call) → per-member client (lock) →
one SDK plan + one mint (`TOKEN_VALIDITY_S`) → `PlanHandle{app plan_id,
armoriq_plan_id only if exposed, token expiry}`. Failure → `BLOCK`/`UNVERIFIED`
decision in the handle path, never an unhandled raise. Sync SDK calls run off the event loop.

`invoke_step(i)`: fresh `jti` → `sign_ctx(request/plan/step/tool/aud)` (P1-04 interface;
stub until merged) → invoke under same plan/token → map per §7 → HOLD enters background
wait (`APPROVAL_TIMEOUT_MS`, Arch §5.6.3) → approved resumes same plan/step via verified
SDK path with expiry + idempotency checks; everything else no-execution, no disclosure.

`attempt_off_plan`: SDK plan-check path only (`client.invoke(...)` per Arch §6.2),
never executes, never touches the tool server. Label per evidence (E2).

Identity/context boundaries (R-10..R-13, R-23..R-26): identity only from P1-03's trusted
mapping (Slack IDs / signed session → member → env email); gateway is the sole caller of
`armoriq_email_for`; raw emails only in config/identity/gateway (and per ADR-020 the
`_ctx` carries the env-key **ref**, never the raw email); model/request-body identity,
tier, recipient, or `_` keys are rejected by validators and never reach the SDK as
authority; forged `_approvals/_delegation_id/_policy_context` change nothing (P1-04
strips; gateway never treats them as approval); logs carry request/trace/plan/step/jti/
outcome/source only — never tokens, keys, `_ctx`, or unmasked emails.
